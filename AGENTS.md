# Odyssey Master (Beckhoff) Agent Rules

WPF HMI for a Beckhoff / TwinCAT machine. The PLC owns all machine logic - sequences,
motion, interlocks and device alarms. This application is presentation, recipes and
persistence only.

## Projects

- `Nova.Wpf.App` (.NET Framework 4.7.2, C# 7.3): startup/DI, views and services (folder layout below).
- `Nova.Wpf.UI` (.NET Framework 4.7.2, C# 7.3): reusable controls, themes, view resources.
- `Nova.ViewModels` (.NET Standard 2.0, C# 8.0): platform-free ViewModels. Depends on `Nova.Abstractions` only.
- `Nova.Abstractions` (.NET Standard 2.0): interfaces/contracts only.
- `Master.Repository` (.NET Standard 2.0, C# 7.3): SQL Server / CSV data access for `TEAL_Master` (`IDataAccess`), and the `Nova.Abstractions` repository contracts implemented directly over it (`AlarmLogRepository`, `AlarmHistoryRepository`, `ProductionRepository`, `ReportRepository`, `ShiftSettingsRepository` in `Repositories\`). `MasterDatabase` picks SQL Server or the CSV fallback and builds them; the app registers its repositories as they are. ViewModels still see only the `Nova.Abstractions` interfaces.
- `Master.Configuration` (.NET Framework 4.7.2): reads the device configuration (`Data\*.json`, including the PLC card in `CardsConfiguration.json`) into `ConfigGlobalClass` through `MachineConfiguration`, and creates the Beckhoff library object for every device on the one card through `DeviceObjects.Create` (keyed by its own enums in `StepperObjects`, `ServoObjects`, `CylinderObjects`, `VacuumObjects`, `CCDObjects`, `ScannerObjects`, `RobotObjects`, e.g. `StepperObjects.StepperMotorObj[Steppers.LiftingStepper0]`). The app reads device configuration and gets library devices only through it, never from the JSON files directly; `TwincatDevices` only wraps them in adapters.
- `Nova.Alarm` (.NET Framework 4.7.2, C# 7.3): subscribes to the PLC's alarm list (`GVL_Alarm.fbAlarmManager.aAlarms`) with ADS notifications (no polling), works out when each alarm starts and ends, and saves them to the `[Alarms]` table through `IAlarmHistoryRepository` (`Nova.Abstractions`; Master.Repository's `AlarmHistoryRepository`). It does not reference Master.Repository. Also holds `PlcSubscriptions`, the shared ADS-notification engine every live PLC status goes through.
- `Master.SharedUtilities` (.NET Framework 4.7.2, C# 7.3): what Master.Scheduler uses from Odyssey.Master_V3's project of that name, nothing more: `ShiftStatusHelper` (shift row, OEE, health, production CSV), `StatusDataCalculator`, and `GlobalClass` cut down to the state they work on (`DataAccess`, `CurrentShift`, `Health`, `ShiftStatusData`). References Master.Repository only. The rest of V3's project (pallets, PDATA, serial/TCP/RFID, cycle-time and machine-mode globals) was left out: the PLC owns those here.
- `Master.Scheduler` (.NET Framework 4.7.2, C# 7.3): taken over from Odyssey.Master_V3, the HMI's only housekeeping (there is no `DataRetentionService` any more). `App.OnStartup` calls `ScheduleJobs.Start(MasterDatabase.DataAccess)` (null without a database), which sets `GlobalClass.DataAccess` / `CurrentShift` and starts the Quartz jobs; `ScheduleJobs.Shutdown` on exit. Jobs: `DeleteFilesJob` every 2 min (every `*.csv` under App.config `LogFilePath`, `MachineRecordStore` files included, last written more than `RetentionDaysForCSV` days ago); `ShiftStatusRefresherJob` every `StatusRefreshSeconds` (shift row, OEE with `IdealCycleTime`, and the shift change V3's ShiftMonitor did: final status and `ProductionData.csv`); at 23:30 the alarm, health, production and shift status rows past `RetentionDaysFor*` and the OEE rows before today. The database jobs do nothing without a database. A retention of 0 keeps nothing. The shift times are the `[Shift]` table (`Master_Teal_db_Schema.sql`; a V3-made database has `[ShiftMasterData]` instead and `SQLDataAccess.ShiftTable()` uses whichever exists): with neither readable the current shift is null, `ScheduleJobs.Start` logs an error, and no health, shift status or OEE is recorded. `[HealthData]` (run / down / idle time) is fed by `MachineHealthRecorder` (Nova.Wpf.App\Services\Logging) from `E_MachineState`, started after the scheduler and only with a database: AUTO_RUNNING = RunTime, ALARM = DownTime, IDLE / PAUSE / HOMING / MANUAL / STOP = IdleTime, PLC not live = not counted. Each state change writes the segment before it through `ShiftStatusHelper.SetHealthCategory`; the open segment is added to `GlobalClass.Health` as it goes (read again on every refresh), split at a shift change (`SplitHealthSegment`), and written when the HMI closes. The Home page's State Changes chart reads it back (`HealthStateHistory` in Master.Repository, `IHiveStateHistory`, built by `MasterDatabase.CreateStateHistory` with `ShiftStatusHelper.OpenHealthSegment` for the part not written yet): RunTime = running, IdleTime = idle, DownTime = downtime, a time no row covers = "No record"; seven days need `RetentionDaysForHealthData` of at least 7, and without a database the chart says there is no history. The HIVE log reader (`HiveLogStateHistory`) is no longer used. A shift runs from its start on the date it started (`ShiftDateOf`: the day before for the part past midnight, to the minute) to its end (`ShiftWindow`, next day for a night shift); at a shift change the ended shift's final status and `ProductionData.csv` use that date and stop at its end. Availability's available time = time elapsed in the shift less its planned downtime and break (minutes, whole shift), taken in proportion to the part of the shift elapsed.
- `Nova.Hive` (.NET Framework 4.7.2, C# 7.3): HIVE reporting (machine state 1/2/5 and errordata) and the alarm pop-up. Depends on `Nova.Alarm`.
- `Master.Sequences` (.NET Framework 4.7.2, C# 7.3, SDK-style; OpenCvSharp4 + OpenCvSharp4.runtime.win 4.11.0.20250507 from `packages\`, restored once with internet): the one sequence the HMI runs itself instead of the PLC, by decision: the 5 axis (kinematic) calibration, SCUD3.1 Kinematic Calibration SOP slides 4 to 12. `FiveAxisCalibration.cs` only starts, stops and reports (Start / Stop / Reset; no pause - the 5-Axis tab's Start calls `Start`, Stop calls `Stop`, which cancels the token, stops every servo and CNC axis and pulses the CNC channel's cycle stop and reset); the steps are `FiveAxisCalibration.Sequence.cs` (`Sequence(teach, settings, token)`): image n = vision `C5A,n`, images 1-9 from the translation table at A0 / C0 / Z0 (A0 = mean of the rotation table's A, C0 = its first row's C, Z0 = the live Z, unless set in the settings), images 10-34 from the rotation table, then the calculation, then a validation pass of images 10-34 at the predicted X / Y / Z. The maths is `FiveAxis\` and is OpenCvSharp's own calls, not our code (`CameraCalibrator` = CalibrateCamera and SolvePnP; `KinematicSolver` = steps 2 to 4.3: EstimateAffine3D, Rodrigues, RQDecomp3x3, SVDecomp, Solve(SVD), then Y_C0 / rx / ry / X_A / Z_A / Lx / Lz, the prediction and the centre error E). Verified only against synthetic data (a known camera, hand-eye and kinematics are recovered to 0.03 mm), never on the machine. Reading of the SOP that is not in the slides: (1) the 9 hand-eye points are coplanar, so R_hand_eye's out-of-plane column is completed as a rotation, and the sign ambiguity (-R, or R turned 180 deg about the camera axis) is settled by which one reproduces the commanded A / C of images 10-34, an RMS above 5 deg refuses to finish; (1b) step 3.1's A / C (the Y and Z Euler angles of RQDecomp3x3, i.e. R = Rz*Ry*Rx) are only exact when C is the outer rotation, while the step 4.2 formulas have A outside C (R = Ry(A)*Rz(C)), so both readings are tried against the commanded angles and the better is used, with a warning when it is the second; (2) E (step 4.3) is the plate centre's XY offset against image 5 from solvePnP, in gantry axes. The SOP gives no limit for E, so none is applied: the screen, the log and the result file show it. `FiveAxis\C5AVisionClient` speaks the protocol sheet (`C5A,index` -> `C5A,1/0,index,U1,V1;...;U49,V49;`, 127.0.0.1:8000) over `SocketClient.cs` (namespace `Teal.Library.Utilities`, in the project); `IFiveAxisMotion` is implemented by `Nova.Wpf.App\Services\Twincat\TwincatFiveAxisMotion`: each pose is one G-code block (`G90 G01 X1=.. Y1=.. Z1=.. B1=.. C1=.. F..`) written to the CNC channel's `sMDIProgram` and started with `bCycleStart` (symbol map `Cnc.Members.Mdi*` / `CycleStart` / `CycleStop`, the PLC's `FB_WriteCNCData`), finished when `bCycleRunning` has gone TRUE and FALSE and every axis is within `InPositionTolerance`. Settings (`Data\Calibration\FiveAxisSettings.json`, `FiveAxisSettings`): plate pitch d and image size have no source, are edited on the 5-Axis tab (Setup row, Save setup, written back into the same file) and are refused at Start while 0; vision address, feed, settle, axis names (HMI names X1 Y1 Z1 A R for reading positions, CNC block names X1 Y1 Z1 B1 C1), `CncMode` (MDI, or Auto: the block + M30 is written to `AutoProgramFile` and run through `sProgramPath` / `bAutoMode` / `bCycleStart`; never run) and A0 / C0 / Z0 overrides. A finished run writes `Data\Calibration\FiveAxisResult_Station{n}.json` (K, D, M_hand_eye, the seven values, E per image) and the log; it is not written to the PLC or to the CNC kinematics. `TwincatCalibrationService` owns the instance and routes the 5-Axis tab (translation and rotation tables side by side, one Edit / Save, one Start / Stop; `FiveAxisViewModel`) to it instead of the PLC's calibration manager. Depends on `Nova.Abstractions` (`FiveAxisTeach`, `IAxis`, `IAxisService`, `ICncAxisProvider`).

## Where to look (folder layout)

Namespaces were not changed when the files were grouped (2026-11-24): a class keeps its old namespace whatever folder it sits in, so find it by folder, not by namespace.

- `Nova.Wpf.App\Services\Twincat\` - the PLC side: `Connection\` (the one ADS connection, status-source contracts, `PlcValues`), `Devices\` (the adapters over the library devices, `TwincatDevices`, axis monitor), `HmiDisplay\` (the C# mirrors of the PLC HMI-display structs and `HmiDisplays` / `HmiDisplayStatus`), `Machine\` (orchestrator, machine-mode link, homing), `Calibration\` (calibration and Static & Dynamic), `Recipes\`, `IO\` (digital IO, robot IO, sensors), `Data\` (dispenser figures, parameter values, third-party device blocks), `Unit\` (the unit hand-off: unit-done watcher, HIVE unit data, audits, NG signal, production log, event counter), `Logging\` (sequence log, custom-log bridge, `CustomLogs\`), `Mapping\` (the symbol map).
- `Nova.Wpf.App\Services\` (the rest) - everything the app implements behind a `Nova.Abstractions` interface, by concern: `Devices\` (axis, cylinder, stepper, vacuum, comm devices, CNC HMI launcher), `Hive\` (HIVE/MES process guards and checks: hash key, nozzle, valve, early warning, MES state, unit image zip, picture count), `Access\` (badge/access control, session, idle logout), `Stores\` (`Json*` files, recipes, consumables, machine context and identity, CSV export), `Logging\` (running log, record files, current shift, health recorder), `Localization\`, `Ui\` (dialog, file dialog, navigation), `Comm\` (MES client). `Config\` holds the IO list loader and the release info.
- `Nova.Wpf.App\Views\` (Auth, Common, Dialogs, Pages, Shells), `Converters\`, `Data\` (shipped defaults, copied to the machine's data folder), `Localization\` (resx, left in place on purpose).
- `Nova.Hive\` - `State\` (service, state machine, settings, error codes), `Gateway\` (client, payload, unit data), `Audits\` (audit sessions, NG statistics, dry run IDs, planned downtime), `Plc\` (state and unit readers), `Dialogs\` (every window and prompt).
- `Nova.Abstractions\Services\` - the interfaces, in the same groups: `Access\`, `Devices\`, `Plc\`, `Hive\`, `Mes\`, `Recipes\`, `Calibration\`, `Ui\`, `Settings\`, `Logging\`; `Data\` (models, repositories), `Hardware\`, `Machine\`.
- `Master.Sequences\` - the 5 axis calibration the HMI runs itself (`FiveAxisCalibration`, `FiveAxis\` maths and vision client); its motion side is `Nova.Wpf.App\Services\Twincat\Calibration\TwincatFiveAxisMotion`, its screen `Nova.ViewModels\Pages\Config\Calibration\FiveAxisViewModel` and `Views\Pages\Calibration\FiveAxisView`.
- `Master.Configuration\` - `Loaders\` (the `*Objects` library-device creators, card, DIDO), `Enum\`, `Model\`; `MachineConfiguration` and `ConfigGlobalClass` at the root.
- `Nova.ViewModels\Pages\` is one folder per page: `Home\`, `Alarm\`, `Data\`, `Vision\`, `Config\` (the page, plus its sections: `MachineConfigs\` = the machine configuration tree, `Recipe\`, `Calibration\`, and the `Description\` / `Localization\` tabs), `Setting\` (the Setting page; its tabs are in `Tabs\`), `Manual\` (`ManualViewModel`, then one folder per device kind: `Axis\`, `Cylinder\`, `Vacuum\`, `Stepper\`, `Robot\`, `Camera\`, `ConsoleDevices\`, `ThirdParty\`, `Log\`), and `Shared\` (the page base class and the row models). The Views under `Nova.Wpf.App\Views\Pages\` are not yet grouped the same way. `Nova.Wpf.UI\` is styles, themes, components, behaviors.

## PLC symbol map (read this first)

- Every TwinCAT variable name the HMI uses is in `Nova.Wpf.App\Data\PlcSymbols.json`, read by `Services\Twincat\Mapping\PlcSymbolMap`. `App.xaml.cs` hands each service its section. No other file names a PLC variable: not App.config (its `Plc*Symbol` and `*HmiDisplayType` keys are gone), not a view model, not a service. Where a bullet below still says "App.config `PlcXSymbol`", read "the symbol map".
- A blank map entry means the PLC has no variable for it yet: the function reports itself as not available with the reason. Never substitute a fake value or a simulated success.
- `PlcSymbolCheck` looks every mapped name up once the PLC is live and reports the missing ones.
- `Docs\TwinCAT_Integration.md` describes the communication patterns, what changed against the D-SCUD PLC, and what the PLC still has to provide. Keep it and the `PLC TODO` comments in the map in step.
- Differences from the bullets below, as the D-SCUD PLC is today: the machine buttons are `MAIN.bStartPb` / `bPausePb` / `bStopPb` / `bResetPb` (Stop is real, not Pause); the sequence log is `ST_SeqLog` in `MAIN.seqlog.aLog[n]`; the digital IO is the library card's `GVL_Inputs.Inputs` / `GVL_Outputs.Outputs` (ARRAY[1..n] OF BOOL, named in `CardsConfiguration.json`: `InputArray`, `OutputArray`, `IOFirstIndex`, `InputCount`/`OutputCount`; the symbol map has no IO section); Device Settings is written to the PLC through `IMachineModeLink` and read back; calibration is the PLC's calibration manager and teach tables (GVL_Calibration, GVL_CalTeach; Config > Calibration, see below); the CNC tab jogs through `ICncAxisProvider` (`TwincatCncAxisAdapter`, ids `CNC{channel}_{axis}`) and its positions go to the FB_Recipe of `Cnc.Channels`; finished units go through `PlcUnitDoneWatcher` (a production row in TEAL_Master, the measured coordinates, and HIVE); the glue figures are `TwincatDispenserDataService`; glue weighings and coordinates are kept as daily CSV files (`MachineRecordStore`) and purged by Master.Scheduler's `DeleteFilesJob`.
- The Manual tab's Dispenser, Weighing and Vibration tabs are `PlcDevicePanelViewModel` subclasses (`ThirdPartyDeviceViewModels.cs`) that name what they show and send by logical key; `IThirdPartyDevices` / `TwincatPlcDeviceService` maps each key to a member of the device's PLC block (symbol map: ThirdPartyDevices). One view, `PlcDevicePanelView`, serves all three. A new value on a tab is a key in the view model plus its member in the map.
- Each finished unit is sent to HIVE as machine_data (DFM S1.2, HIVE PayloadSpec 5.6): `PlcUnitDoneWatcher` has `HiveUnitDataBuilder` read the unit while the PLC holds it - `Status.UnitDoneSerial`, `UnitRecord` (Pass and CycleTime are required), every `Parameters` entry under its own name, the consumables, the glue figures and the Spec Limits rows of the same names - and `HiveService.SendUnit` adds hive_state and the audit keys and posts it as multipart/form-data (`jsondata`). Text goes in `serials`, numbers in `data`, limits in `limit`. No 200/201 after `HiveUnitAttempts` tries of `HiveUnitTimeoutMs` puts the machine down with `X03IPOO-01` and the payload joins the 5 minute retry queue; a "Result":"FAIL" answer is logged, the unit's fate is the PLC's. A key with no source is left out, never filled in. For an audit unit (PD-11/13/14) the gateway's error codes 1024 and 1025 count as accepted; any other failure is shown to the OSS. A downtime the HMI raises itself (`HiveService.ReportFault`: hash key error, HIVE upload not confirmed, short picture count) also holds `Process.HmiStopRequest` TRUE until HIVE leaves downtime - the PLC finishes the unit in process and stops.
- `HashKeyGuard` (Nova.Wpf.App\Services\Hive) asks MES `CHECK_AUDIO_INFO` (the hash keys, same `results` string as the PD-15 upload) every time HIVE switches to Running; false puts HIVE into downtime through `HiveService.ReportFault` with MES's text, no usable answer does the same as `X02IPOO-01` unless App.config `HiveHashCheckOnMesError` is "ignore", and with no `MesUrl` nothing is checked.
- `MesStateReporter` (Nova.Wpf.App\Services\Hive) posts every HIVE state change (`HiveService.StateChangeSent`, 5 to 5 included) to MES `/api/machine/collmachinestatefromcard` (S1.1.2): the downtime's error and start time on state 5 and on the 5 to 1 that ends it, empty error fields otherwise, `uid` only for changes made by hand. App.config `MesStateUrl` (blank = MesUrl's host), `MesMachineName` (blank = profile Station), `MesLineName` (blank = profile Line). No `MesUrl`, no report; a false answer is only logged.
- What else happens at the unit hand-off (`PlcUnitDoneWatcher`), each part only when its source is there:
  `UnitImagePackager` (Nova.Wpf.App\Services\Hive) finds the unit's AOI images under App.config `UnitImageFolder` (file or folder name contains the SN), reports the count to `IPictureQuantityCheck.ReportUnit` and adds one zip, `UnitSN_Project_Line_Station_Instance_yyyyMMddHHmmss.zip`, to the payload's blobs (T5); blank folder = not available. `NgStatistics` (Nova.Hive) counts the unit's final result: 3 NG in a row or 5 in total (App.config `HiveNgConsecutiveLimit`, `HiveNgTotalLimit`; per station unless `HiveNgScope` is "machine") is downtime `P99DSOO-01` through `ReportFault`, an NG below that a pop-up and `Process.NgWarningBuzzer`; a unit HIVE's own check failed counts too, one not confirmed does not; nothing counts while HIVE is down or in manual; the counts are in `Data\Settings\NgStatistics.json` and start again when HIVE leaves the downtime they raised. `EarlyWarningService` asks MES `GET_SMART_FA_ALTER_MSG` (S17): false opens `EarlyWarningWindow` (always on top, the machine keeps running, `Process.EarlyWarningLamp` / `EarlyWarningBuzzer` held while open), closed with a card MES checks (`GET_OP_ACCESS`, "UID,Close") unless App.config `EarlyWarningClose` is "confirm".
- `UnitUploadNgSignal` pulses `Process.UnitUploadNg` (serial number first in `Process.UnitUploadNgSerial`) for a unit HIVE refused or did not confirm (S12): the PLC diverts it to the NG conveyor.
- `UnitRecord.AoiStates` (symbol map) lists the glue path AOI state code of each pose by HIVE's key (S16). A listed pose that reads 0 or cannot be read goes out as 0 with both limits 1111111; a pose not listed is not sent.
- PD-12 Nozzle Change (S3.3) runs in the spec's order: `GET_RUBBER_VALVE_STATUS`, the valve double confirmation (a valve with a QR label is scanned and must equal the recorded SN; a model with an internal SN is read from the consumables), then `UPDATE_RUBBER_BODY_SN`. The nozzle SN is the one SN that may be typed (the dialog's "no QR label" box); the first change shows the old SN as "0000". MES's `MAINTAIN_TIME` / `REMAINING_TIME` are kept per gantry and shown on Home's Parameter Dashboard as `Front_Health_Status` / `Rear_Health_Status` (never sent to HIVE). `NozzleHealthGuard` asks MES again at the next switch to Running and puts HIVE back into PD-12 when MES fails the nozzle.
- `ValveSerialMonitor` (S3.1 point 4): for a valve model with an internal SN, the controller's SN (dispenser block member `SerialNumber`) is compared with the one PD-04 recorded (`GantryConsumables.ValveInternalSn`) every `ValveSnCheckMinutes` on the clock; a mismatch or failed read is downtime `G05DSVP-01`. Paused in downtime except LAD (PD-11).
- Audits (S3.4, S3.5): `AuditResultWatcher` uploads PD-13's capture deltas (`RepeatabilityRun`: first capture kept, then max - min so far) and PD-14's results (each checked against its Spec Limits row; one out of spec, or a machine alarm during the calibration, and nothing is uploaded). PD-13 GRR is 30 / 30 / 30 and 10 more as operator 3; PD-14 scans a test SN and is one upload. Cancel at the end of a round ends the run (`HiveService.FinishAudit`): HIVE stays down and another test needs Running and the PD code again.
- The Setting page has two more tabs for Level 2 / 3: Maintenance (`MaintenanceTabViewModel`, `IMaintenanceStore` = `Data\Settings\Maintenance.json`; S11.3: a tile per fixture, Edit only in PD-01 / PD-09, `EQUIPMENT_MT` to MES, hourly countdown, CSV export) and Early Warning (`EarlyWarningTabViewModel`: the S17 test box and the disable switch).
- 24-hour dry run (S4.1): while the HIVE Control tab has it on, `HiveService` takes unit_sn, input_time and mac_addr from `UUID.dll` and unique_machine_state_id (with its state_change_time) from `UMSID.dll` through `DryRunIds` (Nova.Hive), called with App.config `HiveDryRunSiCode`. The DLLs are 64 bit, not in the repository, and go beside the exe (put the RQ DLL package's C# Release files in `References\RemoteQualification`); without them or the SI code the dry run cannot be enabled and the tab says why.
- There is no sample data and no CSV database fallback any more: the `SampleData` key, the `Sample*` sources and `CsvDataAccess` are gone. Without a connection string `MasterDatabase` provides no repositories, and the pages say there is no history. Where a bullet below still mentions sample data, it no longer applies. To check the database screens without the machine, `Master.DB.Scripts\DummyData_Seed.sql` puts seven days of made-up `[HealthData]`, `[Alarms]` (descriptions end in "[dummy]") and `[ProductionData]` (serials "DMY...") into TEAL_Master, recorded in `dbo.DummyDataSeed`; `DummyData_Remove.sql` takes exactly that out again. Never run the seed on a production machine's database.

## Architecture decisions

- The machine's data folder - every `Data\...` file below (device configuration, `PlcSymbols.json`, recipes, `Settings\`) - is App.config `TealDataDirectory`, `C:\TEAL\Data` when blank (V3's folder), resolved once by `App.ResolveDataDirectory` and handed to every service as `dataDirectory`; nothing builds its own exe-relative `Data` path. The `Data` folder next to the exe holds the shipped defaults: at each start every one the data folder lacks is copied in, never over a file already there, so a build or install does not undo what was saved on the machine (change a shipped default on an existing machine by editing the file in the data folder). A data folder that cannot be created is a startup warning and the exe's folder is used. On this PC V3's Advantech-era files were backed up to `C:\TEAL\Backup\Data\V3_20261115` before this app's files replaced them; V3 files this app does not read were left there.
- Master.Configuration's enums (`Master.Configuration\Enum`: `Steppers`, `Servos`, `Cylinders`, `Vacuums`, `CCDs`, `Scanners`, `Robots`) list the machine's devices; each device's settings are the entry with the same `EnumName` in its `Data\*.json` file (`MachineConfiguration.Configured`). Where an enum and its file disagree, `MachineConfiguration.Load` reports it and the device is left out. The Nova contracts cannot reference Master.Configuration, so there a device's `ComponentId` is its enum member's name; there are no device-list enums in `Nova.Abstractions`.
- A device's entry in its `Data\*.json` file has the property names and types of the library class its constructor takes (`CardsConfiguration.json` = `CardProperties`, `Cylinders.json` = `CylinderProperties`, `Vacuums.json` = `VacuumProperties`, `Servos.json` = `AxisProperties`, `Steppers.json` = `StepperProperties`, `Scanners.json` = `ScannerProperties`, `Robots.json` = `RobotProperties`, `CCDs.json` = `VisionProperties`), taken from the DLLs in `References\Beckhoff`. Only fields the HMI itself needs are added: the servos' `ConfiguredPositions`, the TCP devices' `IPAddress`/`Port`, and the card's `VisionDUTName`/`ScannerDUTName`. The Master.Configuration models mirror this, and the `*Objects` loaders copy it across as it is. A cylinder's or vacuum's `Id` is its PLC enum value (`E_Cylinders`, `E_Vacuum`), the index of its block; its valve and sensor names are `Data\Config.csv` points (the PLC's `E_Input` / `E_Outputs` names, which `FB_CylinderMapping` / `FB_VacuumMapping` wire into the block), used only to label the Manual boards, and a name not in Config.csv is a startup warning. There is no I/O GVL prefix (`IoGvl` / `PlcIoGvl` are gone).
- The card's `{DBName}.{ServoDUTName}` (`CylinderDUTName`, `VacuumDUTName`, `StepperDUTName`) is the PLC's mapping block for that kind of device (`MAIN.servocall`, `MAIN.cylindercall`, `MAIN.vaccumcall`, `MAIN.steppercall`), and the library finds each device in it by its `Id`, the PLC array index (1-based): a servo's commands are `servoItf[Id].HMI_CMD`, its status `servo[Id].HMI_DISPLAY`; a cylinder is `CylinderData[Id]` (typeCylFB); a vacuum `vacuumdata[Id]` (typeVacFB, run by FB_VacuumSD `vacuum[Id]`), commanded through its `hmicmd.vacuum`/`hmicmd.blow` (the PLC clears each as it takes it and has no off command), its HMI display the whole `typeVacFB` (App.config `typeVacFB`: sensor in `in`, state in `status`); a stepper `stepperdata[Id]` (ST_STEPPER, run by FB_StepperSD `stepper[Id]` with `config.baxisstepper` FALSE), commanded through `hmicmd` (`bfwd`/`brev`, `bstop`, `breset`; it has no on or off, so `benable`/`bdisable` are not written) - held levels the PLC keeps as written, so each library command also clears the bits that would override it and Reset pulses `breset` for 200 ms - its HMI display `status` (App.config `ST_STEPPER_STATUS`). The library holds those member names. A TCP device's library `InstancePath` is `{DBName}.{VisionDUTName}` (or `ScannerDUTName`), not a field of its own file; the library adds the array, so a scanner is `MAIN.scannercall.ScannerData[Id]` (typeScnFB), a vision `MAIN.visioncall.VisionData[Id]` (typeVisionFB). Its HMI display is its `status` struct (App.config `typeScnFBstatus`, `typeVisionFBstatus`). The PLC acts on a TCP device's `hmicmd` only in `E_MachineState.MANUAL`; the library never sets the machine mode.
- The robots are on EtherCAT, not TCP/IP: a robot is the library's `TwincatRobot` (`Teal.Library.Twincat`), and `Robots.json` holds only its `Id`. - Live PLC status is never polled: each adapter's status symbols are ADS notifications in `PlcSubscriptions` (on the one shared connection), and it reads the values held there. Commands still write through the library.

- A device's status is one struct, its HMI display. The library object says where it is (its `HmiDisplaySymbol`, e.g. `MAIN.servocall.servo[1].HMI_DISPLAY`, read by `HmiDisplays.SymbolOf`); the HMI never builds or configures a status path itself. Its fields are what the screens show - add a field to both the PLC struct and the C# struct when a screen needs one. A missing symbol or a size mismatch is reported at startup.

- The indicator bar's Start / Pause / Stop are the PLC's mode buttons (`TwincatMachineOrchestrator`): each press sets its BOOL in `MAIN.modecall` (App.config `PlcStartSymbol`, `PlcPauseSymbol`, `PlcStopSymbol`) TRUE for 200 ms, as FB_ModeSelection acts on the rising edge. The PLC has no stop input yet, so Stop pulses PAUSE. The buttons are enabled from the PLC's `E_MachineState` (`PlcMachineStateSymbol`, `Watch`ed), never from a state the HMI keeps. The manual-operation GUI (the Manual device tabs), the Homing button and the running log are the Setting page's Manual tab (`ManualTabViewModel`): the device tabs at full width, and their last tab, Log (`ManualLogViewModel`), holds the Homing and reset buttons on top (commands in `ManualTabViewModel`, handed to it as `MachineControls`) and below them the running log and the alarms standing now (`IActiveAlarmService`); the Home page has no Vendor tab. The Homing button waits for the PLC's homing command and done bits (`PlcHomingCommandSymbol`, `PlcHomingDoneSymbol`). It refuses while the PLC is in ALARM or auto running; while homing, the page buttons and Setting tabs refuse to leave (leaving would release manual mode), and a homing the PLC gives up (it leaves HOMING, or goes to ALARM / STOP, without the done bit) ends through `IHomingService.EndHoming`.
- Calibration is the Config page's third section (`CalibrationViewModel`, `Nova.ViewModels\Pages\Config\Calibration`; view `Views\Pages\Calibration\CalibrationView.xaml`, Level 3 like Recipe), one tab per calibration: 9-Point, 5-Axis, Camera Needle, Needle Module. The taught positions are owned by the HMI, one file per calibration in `Data\Calibration` (`NinePoint.json`: X / Y per station; `FiveAxisTranslation.json` (stations 1 and 2: point1 .. point9, X / Y) and `FiveAxisRotation.json` (stations 1 and 2: point10 .. point34, A / C / X / Y / Z), one tab each, saved to the file only and not written to the PLC; `CameraNeedle.json`: per station glue1..9 and vision1..9 X / Y; `NeedleModule.json`: X / Y / Z per station; every station has `Taught`, the PLC's `bTaught`). A new calibration is a `CalibrationTable`, its file, its `CalibrationKind` and its teach array in the map. The Setting page has no Calibration tab any more, and the old routine screens (`CalibrationTabViewModel`, `CalibrationRoutines`, the 9 point request / acknowledge programs, `CalibrationParameters.json`, `CalibrationHistory.json`, the scanner read test) are gone.
- Static & Dynamic is the Calibration section's tab after the four tables (`StaticDynamicViewModel`, `StaticDynamicView.xaml`; `IStaticDynamicService` / `TwincatStaticDynamicService`; symbol map `Calibration.StaticDynamic` = the PLC's `GVL_StaticDynamic`, run by `Static_Seq` / `Dynamic_Seq`). The PLC owns the positions (its recipe rows), the vision commands and the log; the HMI writes `nMode` / `nCcd` / `nIteration` and pulses `bStart` / `bEnd` / `bStop` (200 ms), and shows `bBusy` / `bDone` / `bError` / `nCount` / `sStatus` / `rVisionX/Y/Z` (followed only while the tab is on screen). It runs in AUTO, not manual mode. `nMode` is read by the main sequence for every unit and a non-zero value skips dispensing, so the tab always shows the PLC's mode, confirms before leaving Off and offers Off. Rows go to `MAIN.sdlog` (`ST_SDLog` = `StaticDynamicLogModel`, `CustomLogs.StaticDynamic`, NLog `StaticDynamicTarget`). The reference design's Start / End X / Y inputs and CCD 3 are deliberately absent: the PLC takes no coordinates and serves two cameras (`Cameras`). Details: `Docs\TwinCAT_Integration.md`.
- Beckhoff's CNC HMI (`Beckhoff.App.Shell.Core.exe`, a 32 bit WPF shell with its own ADS connection) is a separate program, started by the "CNC HMI" button on the Recipe page's CNC tab (`ICncHmiLauncher`, `CncHmiLauncher` in Nova.Wpf.App\Services\Devices); it is not hosted in this window and nothing of it is in this solution. Where it is installed is per machine: App.config `CncHmiExe` (its exe or its folder, full or relative to this exe, environment variables expanded), blank = a `CncHmi` folder beside the data folder (`C:\TEAL\CncHmi`). It keeps its own settings in that folder (`System\GeneralSettings.xml` holds the PLC's `PLC_NetID`/`PLC_Portnumber`, set per machine there, not read from CardsConfiguration.json; its `Log\` too), so it must be installed where the user can write, and it expects the CNC PLC variables (`Global_HMI...`) the PLC has to provide. It has no guard against a second copy: a press while it runs brings the running one to the front. The tab holds manual mode while it is on screen, launching changes nothing there, and the Recipe section is Level 3 already.
- `ICalibrationService` (`TwincatCalibrationService`) reads and saves those files and talks to the PLC through the symbol map's `Calibration.Teach` (GVL_CalTeach) and `Calibration.Manager` (GVL_Calibration, FB_CalibrationManager). Save writes the file, then every station's record into the calibration's teach array (`aNinePoint`, `aCameraNeedle`, `aNeedleModule`; pack_mode 1 records, one ADS write per station, sizes checked against what the PLC declares), then sets `bSave` and waits for `bSaveDone` / `bSaveError` (FB_CalTeachStore writes the persistent data). The Calibration section has its own manual-mode switch (letting go of manual sends the PLC to IDLE, homing required) and lets it go when the section is left. The Manual tab, and the Recipe page's Gantry and CNC tabs (their Move / Jog / teach drive the servos, and FB_ServoSD takes HMI commands only in MANUAL), hold manual mode while on screen; the orchestrator counts every holder, so moving between them never clears it.

Other projects use only the `Nova.Abstractions` repository contracts (`I*Repository`), which `MasterDatabase` provides; none of them references `IDataAccess`, `SQLDataAccess` or `CsvDataAccess`. The one exception, by decision, is the V3 code: `MasterDatabase.DataAccess` goes to Master.Scheduler, and Master.Scheduler / Master.SharedUtilities work on it through `GlobalClass.DataAccess`.

The main library's `Teal.Library.Logger` has this Logger / `LogType`, plus `Logger.IsReady` and `CustomLog.cs` (`ICustomLog`, `CustomLog<T>`, rewritten from the compiled DLL because the source was never in the repository): `Update-BeckhoffLibrary.ps1` is safe to run. NLog 6 has no `concurrentWrites` on a file target: do not add it.

Each log needs its NLog target and a `final` rule in `NLog.config` (`ProductionTarget` / `ProductionLogger`, `C:\TEAL_Log_Data\ProductionData`). `CustomLog<T>` / `ICustomLog` are `Teal.Library.Logger\CustomLog.cs` in the main library. The gantry recipe works as Odyssey.Master_V3's: `Data\Gantry.json` (read through `MachineConfiguration.LoadGantry`) lists each gantry module's servos by `EnumName`, each with its `Type` (X/Y/Z/R, one of each per module), `MovementPriority` and `SafePositionPriority`, plus the module's `PlcGantry`; the module's positions are its servos' `ConfiguredPositions` in `Servos.json` (no recipe file of its own - `GantryStructure.json` and `Gantry_<module>.json` are gone). The Recipe page's Gantry tab shows a row per position name found on any of the servos (first-seen order) and per servo the columns `{servo}_Value`, `_Speed`, `_Acc`, `_Dec`; Save writes each group back into that servo's position of the same name (added if missing). A new robot value is its PLC member plus a row naming it - no code change. Rows without a `PlcMember` stay HMI-only. The CNC recipe (Recipe page's CNC tab, `CNCRecipeViewModel`, `Data\CncRecipe.json`) lists the CNC channels; each maps its axes X1, Y1, Z1, A, R, X2, Z2 (A and R rotational) to servos by `EnumName` and holds named positions (the names come from the JSON), each with a value per axis. The tab jogs the mapped servos while a key is held and Teach copies their live positions into the selected position. The positions go through the same service to `{PlcCncRecipeSymbol}[PlcChannel]` (ST_CncRecipe: `aPos[pos, 1..7]` LREAL in X1, Y1, Z1, A, R, X2, Z2 order, `aName[pos]` STRING(30), `nPosUsed`, `bLoaded` cleared first and TRUE last; MAX_POS from `aName`'s size) on Save and each time the PLC comes back; `PlcCncRecipeSymbol` is blank until the PLC has that array.
- Alarms are raised by the PLC into its central alarm list (`FB_AlarmManager`) and cleared by RESET. The HMI's RESET is the small icon-only button beside Homing on the Manual tab's Log page (no caption or tooltip, by decision): `IMachineOrchestrator.ResetAlarms` pulses every BOOL in App.config `PlcResetSymbol` for 200 ms, in order - `MAIN.bResetPb` (MAIN runs `AckAll()` and the device resets on its rising edge) then `MAIN.modecall.bResetPb` (FB_ModeSelection's own RESET, which leaves STOP); MAIN does not pass one to the other. The HMI (`Nova.Alarm`) compares that list with the alarms it is tracking to get each alarm's start and end time.
- The PLC reports what state the machine is in (`E_MachineState`); the HMI (`Nova.Hive`) turns that, plus the alarms, into the HIVE state 1/2/5. Only an operator with a badge can leave downtime (DFM slide 8) - resetting the alarm or pressing Start does not change it. HIVE is off during manual operation (`HiveService.IsSuspended`): while the PLC is in `E_MachineState.MANUAL` or `HOMING` (homing is started from the Manual page), and while any screen holds manual mode (`TwincatMachineOrchestrator.ManualModeHeldChanged` -> `HiveService.SetManualScreenActive`: Manual, Calibration, Recipe > Gantry / CNC; raised before the PLC is told on entering and after it on leaving), except while the PLC is in AUTO_RUNNING or PAUSE, so opening a manual tab beside a running machine does not blind HIVE. The alarm that a manual movement raises (PLC ALARM) therefore does not put HIVE down either. While off: alarms and faults neither put HIVE down nor open the pop-up (it follows `HiveService.AlarmReported`, not the alarm list; the Log tab's active-alarm list still shows them), the PLC's state is not taken in, the idle check stops, a unit entering does not change the state, `Process.HmiStopRequest` is withdrawn (and asserted again afterwards if the HMI's downtime is still on), the chip shows HIVE disabled (so the bar is not red) and cannot be changed. Database rows and the error log are unaffected. When it ends `HiveStateMachine.Resume` takes the PLC's state in and restarts the 90 s idle and 3 s alarm timers, so leaving manual does not change the state by itself; an alarm still active then is reported (downtime, pop-up); one cleared in manual is never sent. The HIVE state from before manual is kept, so a downtime from before still needs the badge.
- There is no simulated mode: the HMI always runs on the PLC in `Data\CardsConfiguration.json`, and does not start without a usable card there. A PLC that is unreachable is reported and retried. A device kind with no driver yet (SFC) lists no device rather than a stand-in.
- The one generated data set is the sample data (`Sample*` in `Nova.Wpf.App\Services`, marked `ISampleDataSource`): App.config `SampleData=true` gives it to the Alarm and Data pages only, which label it "Sample data". Home and everything from the PLC are never generated.

## Packages and moving the solution to another PC

- `NuGet.config` makes `packages\` the global packages folder (with `LocalNugetRepository\` as the first feed), so the solution restores without internet, and turns package restore on whatever the machine's Visual Studio settings say.
- A project's `obj\project.assets.json` holds the absolute paths of the folder it was restored in; copied elsewhere, a build without a restore looks for the packages under the old path ("The package X with version Y could not be found in ..."). Never ship `bin` / `obj` (or `.vs`): delete them before zipping, but keep `packages\`, `LocalNugetRepository\`, `References\` and `NuGet.config`. On the other PC open the .sln in Visual Studio (it restores from `packages\`), or run `msbuild Odyssey.Master.Beckhoff.sln -restore`.
- NuGet restore skips an old-style csproj that has no PackageReference, and the stale `obj` from an earlier restore keeps being imported (that was Master.SharedUtilities, now SDK-style). Master.Configuration and Master.Scheduler are still old-style but each has PackageReferences; a project with none must be SDK-style.
- `Directory.Build.targets` (`NovaCheckRestoreLocation`) stops a build whose assets file was restored for another folder, saying to restore first (it compares the project folder, so WPF's `_wpftmp` project passes).
- Extract the zip to a short path (e.g. `D:\Odyssey`): the deepest `packages\` paths go past Windows' 260 characters under a long folder.
- A new PackageReference must be restored once on a machine with internet before packing, so it lands in `packages\`.
