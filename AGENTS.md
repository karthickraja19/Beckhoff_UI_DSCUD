# Odyssey Master (Beckhoff) Agent Rules

WPF HMI for a Beckhoff / TwinCAT machine. The PLC owns all machine logic - sequences,
motion, interlocks and device alarms. This application is presentation, recipes and
persistence only.

## Projects

- `Nova.Wpf.App` (.NET Framework 4.7.2, C# 7.3): startup/DI, views and services. `Core\` holds service implementations, the sample-data sources and config models.
- `Nova.Wpf.UI` (.NET Framework 4.7.2, C# 7.3): reusable controls, themes, view resources.
- `Nova.ViewModels` (.NET Standard 2.0, C# 8.0): platform-free ViewModels. Depends on `Nova.Abstractions` only.
- `Nova.Abstractions` (.NET Standard 2.0): interfaces/contracts only.
- `Master.Repository` (.NET Standard 2.0, C# 7.3): SQL Server / CSV data access for `TEAL_Master` (`IDataAccess`), and the `Nova.Abstractions` repository contracts implemented directly over it (`AlarmLogRepository`, `ProductionRepository`, `ReportRepository`, `ShiftSettingsRepository` in `Repositories\`), which the app registers as they are. ViewModels still see only the `Nova.Abstractions` interfaces.
- `Master.Configuration` (.NET Framework 4.7.2): reads the device configuration (`Data\*.json`, including the PLC card in `CardsConfiguration.json`) into `ConfigGlobalClass` through `MachineConfiguration`, and creates the Beckhoff library object for every device on the one card through `DeviceObjects.Create` (keyed by its own enums in `StepperObjects`, `ServoObjects`, `CylinderObjects`, `VacuumObjects`, `CCDObjects`, `ScannerObjects`, `RobotObjects`, e.g. `StepperObjects.StepperMotorObj[Steppers.LiftingStepper0]`). The app reads device configuration and gets library devices only through it, never from the JSON files directly; `TwincatDevices` only wraps them in adapters.
- `Nova.Alarm` (.NET Framework 4.7.2, C# 7.3): subscribes to the PLC's alarm list (`GVL_Alarm.fbAlarmManager.aAlarms`) with ADS notifications (no polling), works out when each alarm starts and ends, and saves them to the `[Alarms]` table through `Master.Repository`'s `IDataAccess` (`InsertAlarm`, `UpdateAlarmEndTime`, `GetOpenAlarms`). Also holds `PlcSubscriptions`, the shared ADS-notification engine every live PLC status goes through.
- `Nova.Hive` (.NET Framework 4.7.2, C# 7.3): HIVE reporting (machine state 1/2/5 and errordata) and the alarm pop-up. Depends on `Nova.Alarm`.

## Architecture decisions

- Master.Configuration's enums (`Master.Configuration\Enum`: `Steppers`, `Servos`, `Cylinders`, `Vacuums`, `CCDs`, `Scanners`, `Robots`) list the machine's devices; each device's settings are the entry with the same `EnumName` in its `Data\*.json` file (`MachineConfiguration.Configured`). Where an enum and its file disagree, `MachineConfiguration.Load` reports it and the device is left out. The Nova contracts cannot reference Master.Configuration, so there a device's `ComponentId` is its enum member's name; there are no device-list enums in `Nova.Abstractions`.
- A device's entry in its `Data\*.json` file has the property names and types of the library class its constructor takes (`CardsConfiguration.json` = `CardProperties`, `Cylinders.json` = `CylinderProperties`, `Vacuums.json` = `VacuumProperties`, `Servos.json` = `AxisProperties`, `Steppers.json` = `StepperProperties`, `Scanners.json` = `ScannerProperties`, `Robots.json` = `RobotProperties`, `CCDs.json` = `VisionProperties`), taken from the DLLs in `References\Beckhoff`. Only fields the HMI itself needs are added: the servos' `ConfiguredPositions`, the TCP devices' `IPAddress`/`Port`, and the card's `VisionDUTName`/`ScannerDUTName`. The Master.Configuration models mirror this, and the `*Objects` loaders copy it across as it is, except the cylinder and vacuum I/O names, which get `PlcIoGvl` in front.
- The card's `{DBName}.{ServoDUTName}` (`CylinderDUTName`, `VacuumDUTName`, `StepperDUTName`) is the PLC's mapping block for that kind of device (`MAIN.servocall`, `MAIN.cylindercall`, `MAIN.vaccumcall`, `MAIN.steppercall`), and the library finds each device in it by its `Id`, the PLC array index (1-based): a servo's commands are `servoItf[Id].HMI_CMD`, its status `servo[Id].HMI_DISPLAY`; a cylinder is `CylinderData[Id]` (typeCylFB); a vacuum `vacuumdata[Id]` (typeVacFB, run by FB_VacuumSD `vacuum[Id]`), commanded through its `hmicmd.vacuum`/`hmicmd.blow` (the PLC clears each as it takes it and has no off command), its HMI display the whole `typeVacFB` (App.config `typeVacFB`: sensor in `in`, state in `status`); a stepper `stepperdata[Id]` (ST_STEPPER, run by FB_StepperSD `stepper[Id]` with `config.baxisstepper` FALSE), commanded through `hmicmd` (`bfwd`/`brev`, `bstop`, `breset`; it has no on or off, so `benable`/`bdisable` are not written) - held levels the PLC keeps as written, so each library command also clears the bits that would override it and Reset pulses `breset` for 200 ms - its HMI display `status` (App.config `ST_STEPPER_STATUS`). The library holds those member names. A TCP device's library `InstancePath` is `{DBName}.{VisionDUTName}` (or `ScannerDUTName`), not a field of its own file; the library adds the array, so a scanner is `MAIN.scannercall.ScannerData[Id]` (typeScnFB), a vision `MAIN.visioncall.VisionData[Id]` (typeVisionFB). Its HMI display is its `status` struct (App.config `typeScnFBstatus`, `typeVisionFBstatus`). The PLC acts on a TCP device's `hmicmd` only in `E_MachineState.MANUAL`; the library never sets the machine mode.
- The robots are on EtherCAT, not TCP/IP: a robot is the library's `TwincatRobot` (`Teal.Library.Twincat`), and `Robots.json` holds only its `Id`. Its I/O image is `Robot{Id}_hw_IO_GVL.hwInputs`/`.hwOutputs` (typeRobotFBHwInputs/typeRobotFBHwOutputs, mirrored member for member in `Teal.Library.Twincat\RobotHwIO.cs`; a size mismatch is reported at startup), and its connection is FB_RobotSD's heartbeat check `RobotGVL.Robots[Id].status.connected`. `ReadAllInput()`/`ReadAllOutput()` give every point but the spares, each `_BYTE1`/`_BYTE2` pair merged into one word (`_BYTE1` high). The robot I/O is not in `Data\Config.csv` and not on the I/O Diagnostics page; the Manual > Robot tab shows it through `IRobotIOService` (`TwincatRobotIOService`), read like the digital IO below - every 200 ms, only while the tab is on screen. Inputs and the byte/word outputs are read only; a BOOL output is written with `TwincatRobot.WriteOutput`.
- ViewModels never reference TwinCAT or `Teal.Library.*` types. PLC access goes through adapters in `Nova.Wpf.App` that implement `Nova.Abstractions` contracts over the Beckhoff `Teal.Library.*` library.
- The library is not in this solution: its source is the `Teal.Library.*` projects in `D:\BeckhOffLibrary\BeckhOffLibrary` (`Teal.Library.Twincat\Teal.Library.Card.csproj` builds `Teal.Library.Twincat.dll`), and every project here references the DLLs built from it in `References\Beckhoff`. Library changes are made there; `References\Beckhoff\Update-BeckhoffLibrary.ps1` rebuilds it and copies the DLLs in, then rebuild this solution.
- Live PLC status is never polled: each adapter's status symbols are ADS notifications in `PlcSubscriptions` (on the one shared connection), and it reads the values held there. Commands still write through the library.
- The one exception is the digital IO (`Data\Config.csv`, and the robot I/O above, read the same way), by decision: no subscription. `TwincatDeviceIOService` reads every input and output through the library card's `ReadAllInput()`/`ReadAllOutput()` (bool[] indexed by the point's Id) every 200 ms, only while the I/O Diagnostics tab is on screen (`FollowStatus`, driven by `SettingsViewModel` activating its tabs), and writes an output with the card's `WriteDO`. The PLC variables behind them are the library's (`GVL_IO.aInput`, `GVL_IO.aOutput`).
- When a screen starts showing a device, the library reads its current status first - the library object's `Update...Properties()` (`UpdateAxisProperties`, `UpdateIOStepperProperties`, `UpdateCylinderProperties`, `UpdateVacuumProperties`), once, on a worker thread under the PLC lock - and the screen shows the library object's properties until the PLC pushes the HMI display below; from then on every change comes through the subscription (`HmiDisplayStatus`). TCP devices have no update method and are subscribed for the life of the HMI.
- The Axis tab drives the servos (`Servos.json`); a stepper driven as an NC axis is configured as a servo there, not in `Steppers.json`. `Teal.Library.Stepper` is I/O steppers only (`IOStepper`), and `Steppers.json` lists only those. The Stepper tab drives them: Forward, Reverse, Stop, Reset (no on or off), with running and error as status.
- A device's status is one struct, its HMI display. The library object says where it is (its `HmiDisplaySymbol`, e.g. `MAIN.servocall.servo[1].HMI_DISPLAY`, read by `HmiDisplays.SymbolOf`); the HMI never builds or configures a status path itself. App.config names the struct's PLC type for each kind of device (`ServoHmiDisplayType`, ...), and the C# struct of that exact name in `Nova.Wpf.App\Services\Twincat\HmiDisplay` reads it: same fields in the same order, laid out as TwinCAT does (each field aligned to its own size, `Pack = 8`). Its fields are what the screens show - add a field to both the PLC struct and the C# struct when a screen needs one. A missing symbol or a size mismatch is reported at startup.
- A device's status is subscribed only while a screen shows it: the screen calls `ILiveStatus.FollowStatus()` and disposes the handle when the device goes out of view (`IActivatableTab`, driven by the page and tab hosts). The Axis, IO Stepper and Vacuum tabs follow the selected device; the Cylinder tab follows every cylinder; the Gantry page follows its module's axes and the move axis; a move waiting to finish follows its own axis. What is needed whatever is on screen - HIVE machine state, TCP device connections - is `Watch`ed for the life of the HMI; the alarm list has its own subscription.
- The indicator bar's Start / Pause / Stop are the PLC's mode buttons (`TwincatMachineOrchestrator`): each press sets its BOOL in `MAIN.modecall` (App.config `PlcStartSymbol`, `PlcPauseSymbol`, `PlcStopSymbol`) TRUE for 200 ms, as FB_ModeSelection acts on the rising edge. The PLC has no stop input yet, so Stop pulses PAUSE. The buttons are enabled from the PLC's `E_MachineState` (`PlcMachineStateSymbol`, `Watch`ed), never from a state the HMI keeps. The manual-operation GUI (the Manual device tabs), the Homing button and the running log are the Setting page's Manual tab (`ManualTabViewModel`); the Home page's Vendor tab is empty. The Manual tab holds `PlcManualModeSymbol` (`MAIN.modecall.bManualSelect`) TRUE while it is on screen and FALSE otherwise, the orchestrator rewrites it when the PLC comes back, and clears it when the HMI closes. The Homing button waits for the PLC's homing command and done bits (`PlcHomingCommandSymbol`, `PlcHomingDoneSymbol`).
- Calibration is the Setting page's Calibration tab (`CalibrationTabViewModel`, routines in `CalibrationRoutines`, one per SOP TE010_CALIBRATION procedure). The PLC runs each routine; the HMI picks one station at a time and a routine, keeps each routine's parameters per station (`Data\Settings\CalibrationParameters.json`, Level 2+ to edit), and through `ICalibrationService` (`TwincatCalibrationService`) writes `nStation`, `nRoutine` (E_CalibRoutine = `CalibrationRoutine.Number`) and `aParam[1..20]` (the routine's parameter order) into `PlcCalibrationCommandSymbol` (ST_CalibrationCmd) before pulsing its `bStart` (`bPause`, `bStop`, `bConfirmOk`/`bConfirmNg` for an operator check) for 200 ms. The PLC reports `ST_CalibrationStatus` (`PlcCalibrationStatusSymbol`, followed only while the tab is on screen): state, step, prompt, verdict and `aResult[1..80]`, row by row as the routine lays out its result table. Start is enabled only when the PLC's homing-done bit is TRUE, nothing runs, and the parameters are saved. The Manual and Calibration tabs, and the Recipe page's Gantry tab (its Move / Jog / teach drive the servos, and FB_ServoSD takes HMI commands only in MANUAL), all hold manual mode while on screen; the orchestrator counts them, so moving between them never clears it (clearing it sends the PLC to IDLE, homing required).
- No C# machine sequences, interlocks or monitors - those live in the PLC.
- Each PLC sequence object writes its last log entry into its own `ST_Sequence` (App.config `PlcSequenceLogSymbols` lists them). `PlcSequenceLog` `Watch`es them for the life of the HMI, with a 10 ms change check, and sends each new entry through `Logger.WriteLog`, off the ADS thread: into the Running Log panel, and the `SequenceLog` files (NLog loggers `Sequence_<station>`).
- Recipes are owned by the HMI and written to the PLC. A gantry recipe (the Recipe page's Gantry tab, `Data\Gantry_<module>.json`) goes to the PLC's `FB_RecipeMapping.Recipe[gantry]` (App.config `PlcRecipeSymbol`, `MAIN.recipe.Recipe`; the gantry is the module's `PlcGantry` in `Data\GantryStructure.json`, 0 = not written) through `IPlcRecipeService` (`TwincatRecipeService`): row = position (`Name[row]`), axis = E_Servo (X=1, Y=2, Z=3, R=4, local to the gantry), `Step[row, axis]` = the X/XVel/XAcc/XDeAcc columns as rPos/rVel/rAcc/rDec. `bLoaded` is cleared first, `Step` and `Name` go over whole (MAX_POS/MAX_AXES from their PLC sizes, unused rows zeroed), then `nPosUsed`, `nAxisUsed`, and `bLoaded` TRUE last. Written on Save, and every mapped gantry again each time the PLC comes back to Run (the PLC does not keep it).
- Alarms are raised by the PLC into its central alarm list (`FB_AlarmManager`) and cleared by RESET. The HMI (`Nova.Alarm`) compares that list with the alarms it is tracking to get each alarm's start and end time.
- The PLC reports what state the machine is in (`E_MachineState`); the HMI (`Nova.Hive`) turns that, plus the alarms, into the HIVE state 1/2/5. Only an operator with a badge can leave downtime (DFM slide 8) - resetting the alarm or pressing Start does not change it.
- There is no simulated mode: the HMI always runs on the PLC in `Data\CardsConfiguration.json`, and does not start without a usable card there. A PLC that is unreachable is reported and retried. A device kind with no driver yet (SFC, the light controller) lists no device rather than a stand-in.
- The one generated data set is the sample data (`Sample*` in `Nova.Wpf.App\Core\Services`, marked `ISampleDataSource`): App.config `SampleData=true` gives it to the Alarm and Data pages only, which label it "Sample data". Home and everything from the PLC are never generated.

## Language/runtime constraints

- Keep `Nova.Wpf.App` and `Nova.Wpf.UI` C# 7.3 compatible.
- Keep `Nova.ViewModels` and `Nova.Abstractions` .NET Standard 2.0 compatible.
